## Run order for #4 – #7

Each command stops on failure; none writes outside the run's folder. Rebuilding changes `output/` only.

```sh
R=full-run-ti36vxyf
./unit9 motion-shots   --run $R --resume      # ~15 min; reuses only clips that still pass every gate
./unit9 motion-validate --run $R
./unit9 motion-timeline --run $R              # human-edit.otio (+ .xml)
./unit9 motion-assemble --run $R
./unit9 motion-check    --run $R
./sbph conform output/unit-9-motion-handled/$R/production.json \
  --reference "$HOME/Projects/nonsense/unit-9/svg-film-v01/production/motion-canvas-full/unit-9-motion-canvas-v01.mp4"   # absolute: relative paths resolve from the film root
./unit9 motion-package  --run $R
```

Then follow [resolve-acceptance.md](resolve-acceptance.md) (Resolve may run on a different machine, such as Windows; copy the handoff folder over and the return back): Studio → `./sbph resolve-check HANDOFF`; Free → manual import then `./sbph resolve-record HANDOFF …`.

## Known limits that stay after v1

- Any change to a file under `src/sbph/`, `render/`, or `motion-canvas/` makes **every** existing shot build stale (they are all in the fingerprint). That is the price of the "never trust a stale clip" guarantee; narrowing it to render-affecting files is a possible v1.x change.
- Unit 9's native project depends on the sibling `../nonsense` checkout.
- Resolve edition limits: external scripting needs Studio ([resolve-acceptance.md](resolve-acceptance.md)).
- Human timing and creative acceptance are never inferred from a passing check.
